# AI跨课程知识图谱学习系统
## MVP说明 v0.1

> 这是一份基于现有技术方案的收敛稿。里面的节点数量、主题范围和功能取舍是MVP建议，不是原方案已经确认的事实。开发前仍需由教学人员确认样板数据。

## 1. MVP先解决什么问题

首版只验证一条完整的学习路径：

```text
找到知识节点 → 看懂跨课程关系 → 查看证据 → 做一道题 → 保存学习记录
```

只要这条路径能稳定跑通，就能判断这个系统是否值得继续扩展。首版不追求一次覆盖四门课程，也不把复杂的AI问答作为系统能否使用的前提。

## 2. 建议的首版范围

### 2.1 样板内容

建议先选“计算机组成原理 + 操作系统”的内存管理主题，使用方案中已经出现的TLB、虚拟内存、页表等例子。最终选哪些节点，要由教学人员确认，不能直接把示例当成正式知识关系。

建议规模：

- 15～20个知识节点；
- 10～15条跨课程关系；
- 10道练习题；
- 每个节点和关系都有自编说明；
- 证据先保存书名、课程、章节和页码等定位信息，缺少完整定位的内容标为“待补充”。

这组数据是开发样板。稳定后，再扩展到原方案中的四门课程、91个节点和68条关系。

### 2.2 首版用户

只保留两个角色：

- **学生：** 浏览知识、查看关系、做题、查看自己的学习记录；
- **教师：** 查看样板内容和导入/验收结果，协助确认数据。首版不承诺按班级查看学生统计。

首版不做编辑员和管理员的在线后台。节点、关系和题目先通过已经确认的JSON或CSV文件导入。首版也不承诺按班级隔离数据；如果必须做班级权限，应先补齐用户、班级和成员关系的数据模型。

## 3. 首版要做的功能

### 3.1 数据导入和检查

系统应能从固定格式的JSON或CSV导入节点、关系和题目，并在导入前检查：

- ID是否重复；
- 关系两端的节点是否存在；
- 关系类型是否在允许范围内；
- 必填字段是否为空；
- 题目关联的节点是否存在。

检查不通过时，给出具体错误行，不要静默导入。

### 3.2 图谱页面

首版页面可以比较简单，先保证能用：

- 按课程筛选；
- 按关键词搜索节点；
- 按关系类型筛选；
- 展示节点和关系；
- 点击节点进入详情；
- 首先支持1跳邻接，2跳查询等首版稳定后再加。

### 3.3 节点详情

显示：

- 节点标题；
- 所属课程和章节范围；
- 自编描述；
- 前置或关联节点；
- 与节点有关的练习题；
- 证据摘要和定位信息；
- 当前用户的学习记录（如果已有记录）。

### 3.4 关系详情

显示：

- 起点和终点节点；
- 关系类型；
- 关系方向；
- 机制说明；
- 边界说明（有内容时显示）；
- 证据状态和定位信息。

关系方向和类型必须按关系字典解释，不能只显示英文枚举值。

### 3.5 练习和答题记录

首版只使用已有答案规则清楚的题型，建议先做选择题和判断题。每次提交保存：

- 用户ID；
- 题目ID；
- 是否答对；
- 本次提交时间；
- 关联的知识节点。

简答题如果没有自动评分方案，只能展示参考答案并记录“已提交”，不要把它伪装成自动批改。

### 3.6 学习记录

首版保存两类信息：

- 学习事件：查看节点、打开关系、开始练习等；
- 答题记录：每一次答题及对错。

首版可以显示“未开始、学习中、需要练习、已掌握”等简单状态，但状态更新规则必须写死。例如，先约定“完成关联练习且最近一次答对”才显示已掌握。不要让模型自行猜测掌握程度。

### 3.7 基础答疑

首版不依赖外部大模型，采用可检查的方式：

1. 根据关键词或节点标题匹配知识节点；
2. 命中后返回节点描述、相关关系和证据定位；
3. 用固定模板组织成回答；
4. 没有命中时明确显示“当前知识图谱未覆盖这个问题”。

等这条流程有真实使用记录后，再决定是否加入embedding、Graph RAG或外部LLM。这样即使外部模型暂时不可访问，图谱和练习功能仍然可以使用。

## 4. 首版不做什么

以下内容不放入MVP：

- 四门课程全部内容一次性上线；
- 完整的L1/L2/L3 Graph RAG；
- 多模型切换和自动Prompt优化；
- 教师在线编辑、审核、发布和回滚后台；
- 班级隔离、复杂组织权限和数据看板；
- 学习路径推荐；
- 自动批改编程题；
- 复杂教材原文片段管理；
- Redis、独立图数据库和提前做的复杂性能优化；
- 移动端专项交互、社区和前沿资讯采集。

这些功能不是永远不做，而是等首版验证了学习闭环再决定。

## 5. 最小数据模型

首版可以使用以下实体：

| 实体 | 用途 | 首版要求 |
|---|---|---|
| `User` | 标识学生或教师 | 只保留ID、角色和基本信息 |
| `Course` | 课程信息 | 课程代码、名称 |
| `KnowledgeNode` | 知识节点 | ID、标题、课程、章节、描述、证据状态 |
| `KnowledgeEdge` | 节点关系 | ID、source、target、类型、机制说明、证据状态 |
| `Exercise` | 练习题 | 题目、题型、选项或参考答案、关联节点 |
| `ExerciseAttempt` | 每次答题 | 用户、题目、结果、时间 |
| `LearningEvent` | 浏览等行为 | 用户、资源、事件类型、时间 |

数据规则先固定下来：

- `KnowledgeEdge`是唯一的关系来源；节点内不再保存一份可变的`adjacent_edges`；
- `source`和`target`的含义写进关系字典；
- 节点ID、关系ID和题目ID不可重复；
- 学生只读已经导入的确认数据；首版不做草稿状态；
- 证据不足时保存为“待补充”，不得留空后又在页面上显示为已核验。

## 6. 最小页面

首版只需要以下页面：

1. 图谱页；
2. 节点详情页；
3. 关系详情页；
4. 练习页；
5. 我的学习记录页；
6. 教师只读内容和导入验收页（如果首版确实需要）。

页面之间要能走通一条路径：从图谱点进节点，再点关系，进入练习，提交后回到学习记录。

## 7. 最小接口

接口名称可以沿用原方案，但先写清请求和响应字段：

| 接口 | 用途 |
|---|---|
| `GET /api/v1/graph/subgraph` | 获取节点和1跳关系 |
| `GET /api/v1/nodes/{id}` | 获取节点详情 |
| `GET /api/v1/edges/{id}` | 获取关系详情 |
| `GET /api/v1/exercises` | 按节点获取练习 |
| `POST /api/v1/exercises/attempts` | 提交一次答题 |
| `GET /api/v1/learning/records` | 获取当前用户记录 |
| `POST /api/v1/ask` | 返回关键词匹配后的模板答疑 |

每个接口至少写明：成功返回、参数错误、资源不存在和未登录时的返回方式。不要让前端和后端各自猜字段名。

## 8. 建议固定的首版技术组合

为了让AI连续开发时不漂移，首版先固定：

- 前端：React + Next.js + Cytoscape.js；
- 后端：FastAPI；
- 数据库：PostgreSQL；
- 本地运行：Docker Compose；
- 外部LLM：不是首版启动条件。

这是开发建议，不是原方案已经批准的技术决策。如果团队更熟悉另一套组合，也可以替换，但替换后要在所有开发任务中保持一致。

## 9. 开发顺序

按下面顺序开发，每一步都要能运行和验收：

1. 确认样板节点、关系、题目和关系字典；
2. 写数据格式和导入检查；
3. 建表并导入样板数据；
4. 完成节点、关系和练习查询接口；
5. 完成图谱页、节点详情页和关系详情页；
6. 完成答题、答题记录和学习记录；
7. 完成关键词匹配和模板答疑；
8. 用一条完整路径做部署和验收；
9. 根据真实试用结果决定是否加入外部LLM和后台编辑。

不要先让AI生成四门课程、完整后台和复杂AI架构，再回头补数据和验收。

## 10. MVP验收标准

满足以下条件，才算首版完成：

- 样板数据导入成功，节点、关系和题目数量与清单一致；
- 没有重复ID，也没有指向不存在节点的关系；
- 学生能按课程或关键词找到节点；
- 节点详情能显示关系和证据状态；
- 关系详情能说明方向、类型和机制；
- 练习能提交，结果能再次查询；
- 刷新页面或重新登录后，答题记录不会丢失；
- 已覆盖的问题能返回正确的节点或关系；
- 未覆盖的问题会明确提示，不编造确定答案；
- 学生看不到未导入或未确认的数据；
- 能在规定的本地或学校测试环境中按文档启动；
- 能完整走通“浏览 → 看关系 → 做题 → 看记录”。

首版暂不把“AI准确率85%”“边界召回率70%”和“200并发”当作硬性验收项。等有真实问题集和测试条件后，再单独制定AI和性能验收。

## 11. 每次交给AI的任务怎么写

不要把整份总方案一次交给AI。每个任务只交一块，并附上当前代码和验收条件。任务说明至少包含：

- 本次只做什么；
- 明确不做什么；
- 要使用的字段和接口；
- 一两个真实示例数据；
- 完成后的手工验收步骤；
- 需要补的测试和启动说明。

例如：

> 请只实现“节点详情接口”。使用现有的`KnowledgeNode`和`KnowledgeEdge`表，返回节点基本信息、入边、出边和证据状态。不要添加登录、缓存或AI调用。完成后提供迁移脚本、接口示例、错误返回和一条可执行的测试命令。

每完成一块，就运行、检查和修正，再开始下一块。这样比一次生成整个系统更容易发现问题，也更容易回退。

## 12. MVP之后的扩展顺序

建议按实际使用反馈逐步增加：

1. 补齐四门课程和更多关系证据；
2. 增加教师编辑、审核和发布；
3. 建立AI问答评测集，再接入Graph RAG；
4. 完善学习状态和推荐；
5. 最后再做班级看板、移动端优化和更复杂的性能方案。
