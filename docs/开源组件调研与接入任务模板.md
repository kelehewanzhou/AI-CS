## 0. 文档说明

### 0.1 目的

本文档为项目引入开源组件提供标准化流程和验收标准，确保：

1. **技术一致性**: 新引入组件不破坏已确定的技术栈
2. **业务独立性**: 核心教学规则保留在本项目代码中
3. **可维护性**: 组件停更或需替换时成本可控
4. **质量保障**: 每个引入决策都有明确的验证记录

### 0.2 适用场景

本模板适用于以下情况（按优先级排序）：

| 场景 | 是否使用本模板 | 说明 |
|------|---------------|------|
| 引入新的基础框架（ORM、图谱引擎等） | ✅ 必须 | 会影响数据模型和架构 |
| 替换现有核心组件 | ✅ 必须 | 替换成本高，需完整评估 |
| 引入新的功能模块（RAG、推荐系统等） | ✅ 必须 | 影响业务逻辑 |
| 引入UI组件库或工具库 | ⚠️ 简化流程 | 可跳过POC，但需评估 |
| 升级已有依赖的版本 | ⚠️ 简化流程 | 参考第6节版本升级流程 |
| 常用小工具（lodash、date-fns等） | ❌ 不需要 | 记录在依赖审计即可 |

#### 5.2.1 分层隔离

```python
# backend/adapters/graph_layout.py - 适配层示例
"""
适配层：抽象第三方布局引擎
- 当前实现：使用cytoscape-cola
- 如需替换，只需修改本文件
"""

from typing import Protocol

class LayoutEngine(Protocol):
    def layout(self, nodes: List[Node], edges: List[Edge]) -> LayoutResult:
        """计算布局"""
        ...

class ColaLayoutAdapter:
    """包装cytoscape-cola库"""
    def __init__(self, config: Dict):
        self.config = config
        self.engine = ColaEngine()  # 第三方库
    
    def layout(self, nodes, edges):
        # 转换项目的数据模型到第三方格式
        cola_nodes = self._to_cola_format(nodes)
        cola_edges = self._to_cola_format(edges)
        
        # 调用第三方库
        result = self.engine.compute(cola_nodes, cola_edges)
        
        # 转换回项目的格式
        return self._from_cola_format(result)
```

业务代码只调用适配层：

```python

class GraphService:
    def get_layout(self, subgraph: SubGraph) -> LayoutResult:
        adapter = ColaLayoutAdapter(config={"maxTime": 1000})
        return adapter.layout(subgraph.nodes, subgraph.edges)
```

| 主版本更新（如3→4） | 低 | 通常不升级（除非有强烈需求） |

#### 7.2.2 升级前检查

```bash
# 1. 检查更新日志
# 官方GitHub Releases页面：{项目URL}/releases

# 2. 检查破坏性变更
# 搜索 "BREAKING CHANGE" 或 "major release"

# 3. 检查依赖冲突
pip install {package}=={new-version} --dry-run
pnpm add {package}@{new-version} --dry-run
```

#### 7.2.3 升级执行

```bash
# 创建升级分支
git checkout -b deps/upgrade-{component}-v{new-version}

# 更新依赖
echo "{package}=={new-version}" >> requirements.in  # 后端
pip-compile --generate-hashes --output-file=requirements.lock requirements.in

pnpm add {package}@{new-version}  # 前端

# 验证测试
pytest tests/ -q
pnpm build

# 提交PR
git commit -m "chore(deps): upgrade {component} to v{new-version}"
```

## 附录B：常见问题与答案

### B.1 搜索找不到合适的项目怎么办？

**答：** 有以下几个选项：

1. **扩大搜索范围**：修改关键词，尝试不同的搜索引擎
2. **降低完整度要求**：寻找覆盖80%功能的项目，剩下20%自行实现
3. **组合多个小组件**：用2-3个专一的小库组成完整方案
4. **自行实现**：如果功能相对简单，自行实现可能成本更低

**记录**：将搜索过程和结果保存在第二步的《搜索过程记录》中。

### B.2 评估时发现项目有漏洞怎么办？

**答：** 根据漏洞严重程度判断：

- **高危CVE（评分≥7.0）**：直接放弃此候选
- **中危漏洞**：评估是否有补丁版本；如无，尝试其他候选
- **低危漏洞**：记录在风险清单，继续进行

### B.3 POC验证失败是否必须放弃？

**答：** 不一定。根据失败原因判断：

- **环境问题**：调整本地环境后重试
- **配置问题**：修改配置参数重试
- **小bug**：提issue给上游或自行修复后重试
- **设计不符**：放弃此候选

如重试3次仍失败，则放弃。

### B.4 生产中发现新组件有问题怎么办？

**答：** 根据严重程度应对：

- **关键功能不可用**：立即回滚此组件
- **功能有缺陷**：修复或在适配层打补丁
- **性能问题**：优化配置或替换组件

记录在第七步的《依赖问题记录》中。

### B.5 第三方项目停更后如何应对？

**答：** 参考第七步的《组件停更应对计划》执行。

简单说：
1. 评估是否有安全风险
2. 评估替代方案
3. 制定迁移计划
4. 按计划执行替换

### B.6 什么时候可以跳过某个步骤？

**答：** 根据组件类型判断：

| 组件类型 | 可跳过步骤 |
|----------|-----------|
| 常用工具库（lodash等） | 第四步POC、第五步集成（直接使用） |
| 已有候选的模块 | 第二步搜索（用现有候选） |
| 简单UI组件 | 第五步适配层（直接使用） |
| **架构框架** | 不可跳过任何步骤 |

**原则**：不可跳过的是"决策"步骤（第一、三、八步），其他步骤可根据具体情况简化。

### E.2 AI评估的验证方法：

- 抽查AI提到的源码位置和文档链接，确认信息准确
- 对AI的结论反复提问"为什么"，确保逻辑完整
- 验证AI是否真的运行过代码（而不是凭记忆回答）

### E.3 何时不应该用AI搜索：

- 只有1-2个明确的候选项目时，手工检查更快
- 决策涉及团队共识或业务敏感信息时，不用AI
- 需要与上游项目维护者沟通时，人工处理更好
