# AT-07 问答基线验收

对应任务八、正式架构 §3.7 和 §4.2。使用 `fixtures/` 中四文件结构夹具；其中“已核验”只是测试设定，不代表正式教材证据。

## 前置步骤与接口

1. 按[运行指南](运行指南.md)执行任务一迁移和种子导入；`qa_records` 已由初始迁移创建。
2. 启动 FastAPI，使用已完成首次改密的学生或教师登录。前端进入 `/graph/`。
3. 每个问题向后端 `POST /ask` 发送 `{"question":"问题"}`，携带会话 Cookie、允许的 `Origin` 和 `Content-Type: application/json`。同源前端实际路径为 `/api/v1/ask`，由代理移除 `/api/v1` 前缀。
4. 检查 HTTP 状态、响应结构、实际引用和数据库记录。测试故障注入仅在隔离数据库进行。

成功业务响应 HTTP 200：

```json
{
  "data": {
    "status": "answered",
    "reason": null,
    "answer": "固定模板生成的说明",
    "used_node_ids": ["CO03", "OS02"],
    "used_edge_ids": ["E001"],
    "uncertainty_flag": false,
    "boundary_note": ""
  },
  "request_id": "0123456789abcdef0123456789abcdef"
}
```

七个业务字段均必返。`not_covered` 和 `insufficient_evidence` 仍返回200，但引用数组均为空，`uncertainty_flag=true`，`boundary_note` 说明缺口。技术错误独立返回 `{code,message,request_id}`，不得加入第四种业务状态。`X-Request-ID` 与响应编号一致。

## 额外规则与匿名记录

- 归一化使用 NFKC、casefold、标点换为空格、连续空白折叠；`T.L.B` 保留为 `t l b`，不得拼成 TLB。
- 匹配保留全部出现位置，删除被较长命中严格包含的跨度，然后按标题优先、命中长度降序、node_id 升序排序并按节点去重。短标题在其他独立位置出现时仍计入。
- ASCII 别名采用非 ASCII 字母数字边界；例如“解释OS”“OS是什么”可命中，但 most、xos、os2 不命中。
- 单节点按 edge_id 升序最多引用3条已核验边；双节点按 prerequisite、implements、contrast、boundary 的固定顺序，再按 edge_id 排序，最多3条。
- 已下线节点、边及端点不进入回答。节点和别名每次从当前数据库加载；内容更新后下一次提问立即生效。
- answered 的节点引用是实际使用边端点的去重升序集合；边引用保留选取顺序；边界说明只汇总实际使用边。
- 问题 trim 后保存，最大500字；回答、状态、原因、引用、边界及请求编号与响应一致。业务未覆盖或证据不足也保存快照。
- actor_key 为 `HMAC-SHA256(key=SESSION_SECRET_KEY + ':' + UTC月份YYYYMM, message=user_id)` 的64位小写十六进制值。同用户同月相同，跨月变化；无明文 user_id 列或用户外键。UTC 月份统一不同部署机器的轮换边界。
- 模板和写入失败日志仅记录 request_id、异常类型，不打印问题、异常正文或 SQL 参数。

匿名记录核对 SQL：

```sql
SELECT actor_key, COUNT(*) FROM qa_records GROUP BY actor_key;
SELECT record_id, status, reason, used_node_ids, used_edge_ids,
       uncertainty_flag, boundary_note, request_id
FROM qa_records ORDER BY record_id DESC LIMIT 20;
SELECT column_name FROM information_schema.columns
WHERE table_name = 'qa_records' ORDER BY ordinal_position;
```
